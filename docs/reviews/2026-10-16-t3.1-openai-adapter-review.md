## Findings

### High: credential binding and secret handling

1. **`validate_access` validates the constructor's key, not the `credential` argument** (lines 184–203, 205, 241). The `credential` parameter is only checked for emptiness; both probes use `self._client`, which was built from the constructor's `api_key`. Validating a pending v2 could actually test another key and report the result under the wrong version (PI-05, TC-05).
   - Suggested direction: the key reaches the adapter only through the lease's secret holder inside `open_session`, so the session can't probe anything else.
2. **Plaintext key on a long-lived object** (line 67, `self.api_key`; `credential: str` at line 184). L2 requires a secret holder with a constant redacted repr/str that refuses serialization, with plaintext extraction private to the adapter session (PI-08, TC-08).
3. **The client is built once in `__init__` and never closed** (line 72). L2/L6 call for one `AsyncOpenAI` per lease, created in `open_session` as an async context manager and closed on every exit, including errors and cancellation. A reused adapter instance would share a credential-bearing client across requests (TC-03, TC-12).
4. **The destination can be overridden** (`base_url` parameter, lines 61 and 86). L6/PI-10 require a fixed destination with no caller override (TC-09). Related T3.2 work: L6 also asks for an owned HTTP transport (no redirects, TLS verification, no inherited proxy/org/project settings, response byte cap before deserialization) rather than SDK defaults.
5. **`services/provider_integration/__init__.py` imports the adapter.** `import services.provider_integration` would then require `openai` at import time, which breaks L1 ("only the adapter imports OpenAI") and TC-14. This file belongs to the core track (delivery-plan file ownership) and will conflict with the T2.1 version. Suggested: leave it out of your branch, or make it import nothing, and let the core owner define it. `adapters/__init__.py` is yours.

### High: validation outcomes vs L6

6. **Validation `status` holds invocation error codes.** It returns values like `CREDENTIAL_REJECTED` and `RATE_LIMITED` rather than `valid` / `rejected` / `indeterminate` (L2 `ValidationResult`). Per the L6 table, `rejected` applies only to:
   - 401 with `invalid_api_key`
   - 403
   - 404 `model_not_found`

   Everything else is `indeterminate` (other 401, 429, timeout, connection/408/5xx, 400/413/422, other statuses), with the code carried as `reason_code`. `test_validate_access_maps_provider_statuses` (test file line 107) currently asserts the invocation codes, so it would pass while TC-04 fails.
7. **Probe success criteria are looser than L6.**
   - The text probe returns `VALID` for an empty reply (line 228); L6 needs a structurally valid **nonempty** response.
   - The audio probe's fallback branch (line 263) returns `VALID` even when the response has no `text` string. L6 counts a text string as success, empty included.
8. **The context check is a placeholder** (line 194: any non-`None` context passes; tests use `{"trusted": True}`). That's acceptable if the core performs the real check, but it shouldn't read as a security control. The shared core will pass a verified `CredentialLease` instead.

### Medium: error mapping, defaults and output handling

9. **Some failures map to the wrong code** (lines 288–319).
   - Timeouts and connection errors carry no `status_code`, so they fall through to `INTERNAL_ERROR` (line 319). L6 maps them to `PROVIDER_TIMEOUT` / `PROVIDER_UNAVAILABLE`.
   - Only 500/502/503/504 count as unavailable (line 313); other 5xx become `PROVIDER_RESPONSE_INVALID`.
   - `authentication_failed` is treated as a key rejection (line 295); L6's allowlist has only `invalid_api_key`.
   - The legacy error **type** `insufficient_quota` isn't checked; only `code` is.
   - Classification reads attributes off the exception; mapping the installed SDK's exception classes (`APITimeoutError`, `APIConnectionError`, `APIStatusError` subclasses) would be more robust. Please confirm their attributes against the installed 1.x SDK.
10. **Default models and loose operation names.**
    - `generate_text(model=DEFAULT_MODEL)` (line 100) and `transcribe_audio(model=DEFAULT_TRANSCRIPTION_MODEL)` (line 147) silently pick a model when none is given. L6 wants explicit configuration entries, not fallbacks (PI-04/PI-06).
    - Operation aliases (`"text"`, `"audio"`, `"text_generation"`, lines 197/200) don't match L2's exact `Target` values.
    - `supported_operations()` (line 79) returns bare names; L2 expects immutable operation/model pairs.
11. **An empty generation counts as success** (line 129: `ok=True`, `result=""`). L2 requires `PROVIDER_RESPONSE_INVALID` for an empty or whitespace reply. The 65,536-byte returned-generation cap (L5) isn't enforced yet.
12. **Usage and request IDs aren't normalized** (TC-11).
    - Usage is copied raw: `dict(usage)` at line 280 or attribute copying. L2/L6 want `input_tokens`/`output_tokens` mapped from Chat's `prompt_tokens`/`completion_tokens`, nullable non-negative values, transcription token/duration fields where reported, and no derived totals.
    - `provider_request_id` comes from `response.id` (lines 125, 165, 217, 252). That is the completion object's ID, not necessarily the provider's request ID; please check what the installed SDK exposes.
    - Request IDs are also not yet filtered by the L2 ID rule or checked against the in-flight key.
13. **Audio input isn't constrained** (lines 147–150). Callers can pass their own `filename` and `response_format`. L4 says to discard the caller's filename and generate one from the validated format, with `response_format=json` fixed. The 10 MB size and format checks (L2/L5) are missing.
14. **One 30-second timeout for everything** (line 52). L5 sets 30 s for generation, 60 s for transcription and 15 s for validation, each capped by the remaining overall deadline. With the ports this arrives as `remaining_seconds` per call.

### Medium: tests and evidence

15. **The tests replace the whole SDK with a fake.** `client_factory` returns a `SimpleNamespace` stand-in (test file lines 48, 66, 85, 134). M1 sign-off asks for the real adapter exercised through a **mocked transport**, so the actual SDK request building and exception classes run. Not yet covered:
    - request payload assertions (`store=False`, `max_tokens`, temperature, the fixed system prompt, `response_format=json`)
    - no environment key or base-URL inheritance
    - blocking real network access
    - real SDK exception types
    - the response byte cap and redirects (T3.2)
16. **Version evidence and doc updates are missing.** T3.1 asks for the installed Python, `openai` and HTTP-transport versions plus a read-only check of the SDK's public signatures, recorded in [acceptance tests](../provider-integration/acceptance-tests.md) and the [delivery plan](../provider-integration/delivery-plan.md). Note that `requirements.txt` pins `pydantic==2.6.1`, which doesn't support Python 3.13. Agree on the environment before recording results.
